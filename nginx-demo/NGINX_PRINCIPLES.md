# Nginx 事件驱动架构：原理、概念及相互关系

> 技术知识输入：用于生成教学示意，不是 Nginx 源码或性能压测数据。

## 1. 核心问题

大量 TCP 连接不等于大量同时执行的请求。很多连接只是在等待客户端数据、上游响应或可写缓冲区。为每条连接分配线程会带来栈内存、调度和上下文切换成本。Nginx 用少量 Worker、事件驱动和非阻塞 I/O 管理大量连接。

必须区分：并发连接数（Worker 正在管理的连接）、就绪事件数（当前可尝试读写的事件）和正在执行的处理逻辑（某一刻真正运行的少量代码）。一个 Worker 管理 100 条连接，并不代表同时执行 100 个处理线程。

## 2. Master 与 Worker

Master 负责加载配置、管理 Worker 生命周期、处理信号，以及启动、重载和关闭流程；它通常不处理日常 HTTP 数据。Worker 负责监听/接收连接、维护连接状态、读写事件、HTTP 处理和必要的上游通信。多个 Worker 是独立进程；Worker 数量与每 Worker 的连接数是不同维度。

## 3. epoll 与非阻塞 I/O

在 Linux 上，Worker 将 socket 及读写兴趣注册给 epoll；空闲时在 `epoll_wait` 等待；有 socket 可读、可写或发生相关事件时，epoll 返回**本轮就绪事件**。epoll 只负责发现值得尝试的 I/O，不解析 HTTP，也不执行代理逻辑。

已注册的连接集合和一次返回的就绪集合不同：维护 100 条连接时，本轮可能仅有几个就绪。就绪也不代表完整请求或响应已到齐，只表示此时 I/O 可能取得进展。

非阻塞 socket 在暂时无法读写时返回 `EAGAIN` / `EWOULDBLOCK`，而不是长期阻塞 Worker。Worker 保存连接/请求状态，等待下一次就绪通知。两者互补：epoll 回答“何时值得尝试”，非阻塞 I/O 保证“尝试未果时不被单连接卡住”。

## 4. Worker 事件循环

```text
注册连接与兴趣事件 → epoll_wait → 取得少量就绪事件 → 短步骤处理
  → 需要等待 I/O：保存状态，等待下一轮就绪
  → 否则：继续处理或完成请求 → 返回事件循环
```

这是概念模型而非源码逐行描述。一个请求可跨越多轮循环；Worker 在某连接等待时可推进其他已经就绪的连接。

## 5. 请求与代理路径

典型请求：建立 TCP → 客户端发送 → socket 可读 → Worker 读取/分次解析 → 本地响应或反向代理 → 可写时发送响应 → 关闭或 Keep-alive 复用。

反向代理包含两条独立连接：`客户端 ←→ Nginx Worker ←→ Backend`。客户端侧和上游侧各有读写状态与缓冲区。上游尚未响应、或客户端接收很慢时，Worker 可以等待相应事件并继续处理其他就绪连接。缓冲可在条件允许时缓解慢客户端影响，但仍受配置、内存、磁盘和流式场景限制。

负载均衡在代理时选择上游（例如轮询、最少连接、哈希）；缓存命中时可直接返回内容，未命中或不可缓存时仍访问上游。两者不是 epoll 的功能，也不是事件循环的前提。

## 6. 慢客户端、Reload 与容量

慢客户端：Worker 发送一部分响应，遇到不可写便记录进度、等待可写事件、返回循环；慢连接仍占连接名额、内存、缓冲与超时资源，但通常不会同步地占住整个 Worker。

平滑 Reload：Master 检查新配置、启动新 Worker；旧 Worker 停止接新工作并尽量完成已有连接，随后退出。因此新旧 Worker 可以短暂共存，Reload 不等于立即中断全部连接。

`worker_processes × worker_connections` 只是粗略维度，不保证可服务客户端数。还受文件描述符、上游连接、内存与缓冲、CPU、带宽、磁盘、超时、TLS、Keep-alive 和实际流量影响。“保持连接数”“每秒请求数”“延迟”是不同指标。

## 7. 本教学模型的事实边界

- 演示规模固定为 100 条已建立连接，不代表性能上限。
- 画面区分已连接、等待 I/O、就绪、正在处理及完成/返回等待。
- 少量就绪事件被 epoll 提取；Worker 每轮只推进少数短步骤，不被画成 100 个线程。
- epoll 不执行 HTTP；客户端侧与上游侧连接是独立资源。
- 模型只自动循环，不能作为压测或真实容量数据。

一句话：**Nginx 的关键不是让一个 Worker 同时执行大量请求，而是不被大量等待中的连接拖住，只在事件就绪时推进相应请求。**
